# Cloudflare R2 destination

put.gd uploads to Cloudflare R2 as its own storage service, `cloudflare-r2` (#1678). It talks
to R2's S3 API through put.gd's S3 adapter, so uploads, links, cleanup and History behave as
they do for [S3](s3.md). You give it the account and bucket; it works out the endpoint, signs
every request with the region `auto` and names the bucket in the URL path.

## Setting it up

1. In the Cloudflare dashboard, create the bucket under **R2 Object Storage**. R2 bucket names
   have 3–63 lowercase letters, digits and hyphens, and start and end with a letter or digit.
2. Under **R2 → Manage API tokens**, create an API token with **Object Read & Write**, limited
   to that bucket. Its **Access Key ID** and **Secret Access Key** are what put.gd needs. A
   token limited to the bucket can't read the bucket's settings; put.gd doesn't need it to.
3. In put.gd, **Destinations → Add destination → Cloudflare R2**. Then either:
   - paste the bucket's **S3 API** address from the bucket's settings page into **Account ID**,
     such as `https://ACCOUNT.r2.cloudflarestorage.com/my-bucket`. It fills **Account ID**,
     **Jurisdiction** and **Bucket** at once; or
   - enter the **Account ID** (32 lowercase hexadecimal characters, digits and letters a to f,
     from **R2 overview → Account details**), choose the bucket's **Jurisdiction** (Default, EU
     or FedRAMP), and enter the **Bucket**.

   **Folder in bucket** is optional (at most 1022 bytes): uploads go into that folder when it is
   set, and to the top of the bucket when it is empty.
4. Choose who can open files (see [Links](#links)), then enter the **Access key ID** and
   **Secret access key**. **Save to keychain** saves them in the system keychain; **Use for
   this session** keeps them until put.gd quits.
5. Press **Test upload and link**. It uploads a synthetic file, checks its link and removes it.

A pasted address is used only when every part of it is valid: the account, the jurisdiction
and a bucket name with nothing after it but an optional trailing `/`. The host may be in upper or
lower case and Account ID is stored in lower case; the bucket name must already be lower case. Anything else, including a percent-encoded address, stays in **Account ID** with a
message saying what Account ID takes. Typing never fills the other fields; only a paste (the
Paste shortcut, Shift+Insert or the field's menu) or finishing an edited address does.

An address with no bucket, such as `https://ACCOUNT.r2.cloudflarestorage.com`, fills Account
ID and Jurisdiction. **Bucket** stays as it is when the account and jurisdiction are the ones it
was entered with (or when it was entered before any Account ID), and is emptied when either
changes. Typing a new Account ID by hand works differently: once it is valid, it saves with the
Bucket already shown.

Account ID, Jurisdiction and Bucket save together, as one group, and only once all three are
valid. Until then they keep
their saved values, the field to fix says why, and the line under Bucket says "Account ID,
Jurisdiction and Bucket save together once all three are valid." If put.gd refuses them, none of
the three is saved and that line gives the reason. On a destination already saved as Cloudflare R2, its other fields, such as its
name and links, save on their own. A new Cloudflare R2 destination, or one switched to R2, is
saved as a whole once all three are valid. Until then, choosing it as where captures go waits to
save too, and captures keep going where the saved settings send them. An
unfinished R2 destination doesn't stop you saving other destinations.

R2 has no regions, so there is no Region field. The location the dashboard shows, such as
"Western North America (WNAM)", isn't needed anywhere. The endpoint put.gd uses is shown under
**Advanced connection settings**: `https://ACCOUNT.r2.cloudflarestorage.com`, with `.eu` or
`.fedramp` before `.r2` for those jurisdictions. Those three jurisdictions are the only ones
the form takes: a bucket in any other, such as one whose S3 API address has `.us`, isn't
supported by the Cloudflare R2 destination.

## Links

- **Private bucket: links that expire** (the default for a new R2 destination): each link is a
  signed link to the R2 endpoint that works for 1–7 days. put.gd doesn't change the bucket's
  own access: public access already turned on for the bucket in the dashboard stays on. A link
  is signed with the API token's keys, so it stops working early if that token expires or is
  revoked before the link's chosen lifetime ends. Copy link in History makes a fresh one after
  the link expires.
- **Public bucket: links that never expire**: R2's S3 endpoint never serves files without a
  signature, so public links need the bucket's public address in **Link domain**. In the
  bucket's **Settings** in the dashboard, enable its **Public Development URL** (r2.dev) or
  connect a custom domain, then paste that address, such as `https://pub-….r2.dev`, into **Link
  domain**. With public links and no Link domain, Settings says so under Link domain, and an
  upload or **Test upload and link** is refused before anything is sent. The bucket's S3 API
  address isn't accepted as a Link domain, because it doesn't serve public links.

## Existing S3 destinations on R2

An Amazon S3 / S3-compatible destination whose endpoint is an R2 account endpoint keeps
working as it is: requests to R2 sign with `auto` whatever Region holds (#1688), including a
saved `aws-global`. Settings offers **Move to Cloudflare R2** for it when its endpoint is an
HTTPS R2 account endpoint (`https://ACCOUNT[.eu|.fedramp].r2.cloudflarestorage.com`, with no
port, path other than a trailing `/`, user, query or fragment), its bucket is a valid R2 bucket name, and its storage
class is STANDARD. Nothing changes until you press it.

Move converts the destination in place: the same name and ID, so the capture default,
exceptions and hotkeys still point at it, and the same saved credentials. Account ID and
Jurisdiction are read from the endpoint. The bucket, Folder in bucket, who can open files, how
long links last, Link domain and the advanced connection values are kept. One exception: with
expiring links, which don't use Link domain, a Link domain R2 couldn't use is cleared. If R2
would refuse the moved settings, for example a public Link domain on plain HTTP, Settings says
what to fix first, nothing moves, and an agent gets `r2_move_refused`. Uploads already in
History keep the destination they were recorded with.

## How R2 differs from S3

- R2 returns a version ID on every write but has no versioning: a request that names a
  version gets 501, and the bucket reports no versioning status. put.gd then checks and
  deletes the object as unversioned and records `versionless` in the deletion journal (#267).
- An API token with **Object Read & Write** limited to the bucket covers everything put.gd
  does on R2 (#1677): uploads, **Test upload and link** and its cleanup, History deletion, and
  expiring links with **Refresh and copy link**. That token can't read the bucket's settings,
  so R2 answers `GetBucketVersioning` with 403. put.gd then takes R2's 501 to a request naming
  a version as proof that the key holds one object. The object must still match its recorded
  publication ID, SHA-256, size and ETag, and a versioning check that reports versioning
  enabled or suspended overrules the 501. Expiring links are then signed without a version
  ID. One extra HEAD naming the `null` version is sent only when a deletion still needs that
  proof: the object it is about to delete has no version to name, the versioning check got
  403 or 501, and no HEAD naming a version was refused earlier in the same check.
- R2 ignores `If-Match` on `DeleteObject`, so a removal is guarded by put.gd's HEAD check of
  the upload's identity, SHA-256, size and ETag just before it, not by the DELETE itself. R2
  also ignores `x-amz-mp-object-size`.
- Conditional writes, multipart uploads, ListParts resume, abort and History deletion work.

## Agents

`ui.r2Destination` (`putgd-cli`) and `drive_r2_destination` (MCP) inspect and edit the form,
paste an S3 API address, add an R2 destination and press **Move to Cloudflare R2** as a user does.
A control a person couldn't use at that moment answers `control_unavailable`: Move where it isn't
offered, Add while it is disabled, or picking another destination by ID while the destination list
can't be used. See
[cli.md](../automation/cli.md) and [mcp.md](../automation/mcp.md). Settings changes can also go
through `settings.patch`: a `cloudflare-r2` profile's settings are described in
[configuration.md](../design/configuration.md).
