# Resident floor: next opportunities after the UI split

Read-only analysis, 2026-10-09. Current source inspected: `9d142919e5e6365227a4424212380e92f85285fe` (source 45). This unit ran no app, measurement, build, guest command, graphical action, credential access, package change or commit. It changes only this scratch note. Root owns the in-progress Settings startup experiment and any later memory proposal. Nothing here is an approved experiment or a measured optimization.

## What remains above 40 MiB

The retained five-minute **source-41 physical Cinnamon cold** observation is 44.390625 MiB RSS, 24.7822 MiB PSS and 22.2891 MiB private. Its RSS gap is 4.390625 MiB. The cold run had no helper, view, capture or active operation. It is not a measurement of source 45. The split already released complete view-helper address spaces: two matched empty-view runs per build reduced median closed-family RSS from 65.09 to 45.04 MiB and PSS from 40.40 to 25.40 MiB. The outstanding gap therefore is not solved by further destroying Settings controls while the helper is already absent.

Cold mapping attribution includes 3.2734 MiB Qt Widgets, 4.9375 MiB Qt Gui, 3.8047 MiB Qt Core, 3.2383 MiB GTK, 2.9141 MiB heap and 1.0625 MiB anonymous memory. These categories are page attribution, not reclaimable allocation totals. Even the hypothetical removal of every recorded heap and anonymous page would be under the 4.39 MiB gap, and most of those pages contain live required state. `OperationService` already requests `malloc_trim(0)` after a two-second idle gate and on startup, with no active work, payload lease, worker or selector.

The existing four-run style probe retained native Cinnamon integration. Native `QApplication` construction alone had a median 39.4805 MiB RSS before style and tray. The settled full-versus-native-style diagnostic difference was only 0.629 MiB; immediate stylesheet allocation was 0.1875 MiB. It used five-second stages and an inert tray, so neither figure is a product saving or a fixed lower bound. Still, these observations make another stylesheet reduction or integer packing a weak candidate for the full remaining gap.

Do not describe KDE's source-41 post-use 145.50 MiB RSS as 145.50 MiB of heap: its quiet PSS was 45.17 MiB and private memory 32.76 MiB. A separate mapping snapshot contained LLVM at 48.28 MiB RSS but 5.98 MiB PSS / 2.14 MiB private. GTK on GNOME was 5.14 MiB RSS but 1.30 MiB PSS / 0.20 MiB private. Native fonts and dialogs remain required; GTK/KDE libraries cannot simply be disabled to satisfy RSS. These are post-use guest observations, not matched cold gains or leaks. Summed process-family RSS also charges shared pages in each process; report RSS, PSS and private together without substituting PSS for the user's RSS target.

## Actual dependency boundary

`src/main.cpp` constructs `QApplication`, applies native-aware styling, creates `TrayController`, then serves operations and launches `putgd-ui` on demand. The tray owns both `QSystemTrayIcon` and `QMenu`; both are Widgets. `CMakeLists.txt` still links Widgets through the executable, `putgd_tray` / `putgd_visual`, `putgd_x11`, and `putgd_kde`. Merely moving Settings or changing the application constructor cannot remove that closure.

Cinnamon uses a custom XCB connection for shortcut grabs and clipboard import, but clipboard **result ownership** calls Qt `QClipboard`. Monitor identity/scaling/window exclusion and screen capture use `QGuiApplication` / `QScreen`; region selection is a translucent QWidget surface. Thus a Gui-only resident is plausible after replacing the tray/menu and overlay surfaces. A Core-only resident additionally needs native clipboard result ownership and a separate capture/display-layout boundary.

GNOME is closest to a Core-only service: the Shell extension already owns shortcuts, selection, capture and copied result data. `GnomeAdapter.cpp` uses `QGuiApplication` only for its native-Wayland platform guard. A Core-only experiment would need a positive session/bridge identity check, not removal of the guard without replacement. Image decoding and shortcut types still link Qt Gui through `putgd_core`, so Core-only application construction does not mean all Gui code disappears.

KDE data-control already maintains an independent `wl_display`, socket notifiers and native result ownership; its QGui dependency is principally the platform guard. KGlobalAccel and ScreenShot2 are D-Bus contracts. However, monitor geometry, target-self exclusion and layer-shell region surfaces still use Gui/Widgets. ScreenShot2 explicitly checks the restricted desktop entry against the **resident executable**, so moving that native request to a different helper requires a deliberate permission/identity change. Prefer retaining native acquisition authority in the resident while an ephemeral selector returns bounded geometry and a dismissal acknowledgement.

Qt's documentation says [QGuiApplication](https://doc.qt.io/qt-6/qguiapplication.html) provides graphical event handling, desktop settings and clipboard services, while QWidget applications need QApplication. [QSystemTrayIcon](https://doc.qt.io/qt-6/qsystemtrayicon.html) belongs to Widgets. This supports identifying dependencies, not estimating product savings. The minimum implementation API stays Qt 6.4.2; current online documentation also includes newer APIs.

A native StatusNotifier implementation is a realistic small protocol component, not a visual-framework rewrite. KDE's authoritative [item interface](https://raw.githubusercontent.com/KDE/kstatusnotifieritem/master/src/org.kde.StatusNotifierItem.xml) exposes icon identity/data, tooltip, activation, context menu and an object-path Menu property; the [watcher interface](https://raw.githubusercontent.com/KDE/kstatusnotifieritem/master/src/org.kde.StatusNotifierWatcher.xml) provides item registration and host/item lifecycle signals. These interfaces confirm a possible Qt Core/DBus boundary. They do **not** provide the complete exported menu protocol or guarantee every desktop has a host. A proposal must inspect actual Cinnamon/GNOME/KDE hosts, preserve current no-host behavior, implement menu export and notification interactions, and account for XEmbed fallback where supported. Simply exporting an icon and dropping the menu is not parity. Source 45 fixes late Qt tray registration; a replacement must keep that behavior.

A permanent Widgets tray helper alongside a Core resident is weak for the total closed-family target: it leaves graphical initialization alive in another process and adds IPC/Core duplication. A Core resident with host-rendered SNI and no permanent graphical helper is the useful distinction. Qt Widgets remain the normal settings/history toolkit; no new custom text/input/accessibility framework is indicated.

## Reproducible future experiment contract

1. Freeze a clean, versioned current baseline and exact source archive; log actual distro Qt/theme/session, resolution/DPR, CPU/observer and executable/module hashes. Prior source-41 results explain the target but cannot stand in for a new baseline.
2. Do not start a product variant until a locator isolates a material cost. Use distro dynamic Qt, standard CMake presets/Ninja and no new guest Node runtime or substitute toolchain. Record separate location evidence and product scoring.
3. Keep current CLI/MCP/private protocol, one resident, tray, native fonts/dialogs, credential store, four capture/clipboard actions, live background, draft conflicts, exact delete acknowledgements, ongoing uploads, helper normal exit and shortcut rebinding. A platform guard must be replaced by a positive checked contract, never silently deleted.
4. Run current-source native functional gates in parallel on existing visible VM overlays; physical Cinnamon timings stay serial. Then collect two alternating baseline/candidate whole-family cold runs of 300 seconds plus matched view/capture/post-use workloads. RSS/PSS/private and process-family counts must all be reported. Preserve failed attempts; RSS changed by desktop page sharing is not private-allocation proof.
5. Save exact commands, structured JSONL samples/results, version/source/binary hashes, fixture definition, operation IDs, native visual receipts, dependency mappings and decision markers. Measure menu-first-click / Settings / selector latency too, so a memory saving cannot hide a usability regression. Reject a variant that needs persistent hidden Qt helpers or drops native functionality merely to reach a number.

No cstdint conversion, narrow integer sweep, packing, global graphics/theme override, clipboard eviction, blind SQLite purge or repeated forced trim is supported. History already prepares bound statements, pages results at 200 and closes per-worker connections. Connection/statement reuse can be investigated for **latency** separately, with explicit thread ownership and disposal; it is not a measured cold-memory remedy.
