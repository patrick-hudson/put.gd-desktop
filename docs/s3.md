# S3 adapter

The official pinned AWS C++ SDK performs S3 signing and HTTP requests. AWS headers
remain under the S3 implementation. Shared acquisition, archive, operation, history
and CLI services use provider-neutral requests and receipts.

Each profile/revision supplies its bucket, region, endpoint, object prefix, storage
class, ACL mode, addressing mode and optional public URL base. The development
configuration is an explicit import, never an automatically activated destination.
`public-read` sends its selected ACL; `omit` sends no ACL header. The adapter never
changes ACL selection, bucket policy, ownership, retention, versioning or DNS.
`AccessControlListNotSupported`, authentication and permission errors are terminal
setup outcomes with retained artifacts. Explicit public URL testing is independent.

Requests verify HTTPS certificates. Plain HTTP is accepted only for a literal
loopback address, enabling a local S3-compatible endpoint and offline fixture.
Path addressing handles dotted buckets, including put.gd. Virtual addressing rejects
dotted buckets and literal IP endpoints; auto selects virtual addressing only for
an AWS endpoint and a bucket without dots. Public URL keys encode each segment once.
An encoded custom base path, including `%2F`, is preserved. A custom share domain is
never an AWS signing endpoint. Without a custom base the effective S3 object URL is
derived from endpoint/addressing/bucket/key.

A single adapter worker serializes SDK calls with at most 32 queued requests, one
connection, one SDK executor thread and at most eight cached client configurations.
The SDK client retains a copied explicit credential generation. Old clients drain
before runtime shutdown. SDK automatic retries are disabled. Its supported Curl HTTP customization also
forces fresh/nonreusable connections for DELETE to prevent libcurl from transparently replaying
a marker-creating DELETE after a reused connection loses its reply. Each DELETE
therefore pays a fresh connection/TLS handshake cost; PUT and HEAD retain connection
reuse. The hook is [the SDK Curl customization API](https://github.com/aws/aws-sdk-cpp/blob/1.11.907/src/aws-cpp-sdk-core/include/aws/core/http/curl/CurlHttpClient.h).
Non-curl SDK builds retain their default HTTP factory and expose deletion as
unsupported until their transport replay semantics have been implemented/verified;
no non-Linux deletion acceptance is claimed. Uploads allow three
total transient attempts with the same immutable key, body and condition, reconciling
publication before another attempt. Explicit connect, whole-request and low-speed
limits come from the profile. Services suppress clipboard results after cancellation;
queued work and later request phases observe a transient cancellation flag. An
already-sent request drains and may have taken effect. No GUI thread streams artifacts
or waits on HTTP. Shutdown waits for resources; configured timeouts bound that wait.

Signed HEAD checks a proposed key; only the final conditional PUT guards the race. New objects use `If-None-Match:*`; explicitly
configured overwrite uses the checked opaque ETag in `If-Match`. A changed/deleted
precondition is never refreshed automatically. Shared naming checks all batch items,
handles original basenames/generated names, caps searches at 32 and handles
rename/skip/overwrite conflicts. It persists candidate, hash, item publication identity
and condition before PUT. The adapter verifies the retained private artifact and
streams it. Object metadata contains publication identity and SHA256; ETag is never
interpreted as SHA256. Lost successful replies and subsequent 412 recover only when
HEAD matches publication identity, hash and byte count. Inconclusive/foreign outcomes
after an ambiguous attempt retain unknown status at the same key. Stable keys do not
promise exactly one version in a versioned bucket.

Receipts contain the exact original non-secret destination, credential reference,
key, version ID, publication identity, SHA256, byte size, ETag and stored direct URL.
Delete never derives a target from the share URL or edited profile. Signed identity
checks precede mutations. Unversioned and mutable null-version removal use the saved
ETag; null-version deletion addresses `versionId=null`. A current immutable version
in an enabled bucket is first hidden by an ETag-guarded delete marker, then only its
recorded bytes are removed. A noncurrent recorded version is removed directly while
preserving the current replacement. Unrecorded versions are never listed or purged.
An original unversioned receipt with no recorded version ID cannot be retargeted
to a newly visible null version after bucket versioning changes; it returns
unsupported_safe_removal without DELETE. Mutable null deletion can reveal an older version; it removes only the recorded
null version and does not claim the public URL or all versions are erased.

Before creating a marker in a suspended bucket the adapter explicitly reads the
null version. Any unselected null object/marker or denied/inconclusive read returns
`unsupported_safe_removal` with no DELETE. Confirmed absence allows marker creation;
bucket versioning is rechecked before it. External bucket versioning changes remain
outside S3's object guard. The ETag precondition cannot distinguish an external
identical-content replacement; this is a documented residual S3 race, not full
version compare-and-swap.

Deletion checkpoints persist intent and result for each destructive step and await
acknowledgement before sending it. Partial removal retains the marker and returns
`hidden_version_retained`; retry targets exactly the recorded immutable version.
A lost removal reply reconciles the exact target. A lost marker reply stays
`delete_unknown`: S3 markers have no publication metadata, so current absence alone
cannot identify this operation's marker. Retry/restart never blindly creates another
marker or adopts a replacement. Permission, retention, MFA and precondition failures
are reported; no bypass is attempted. Local copies/history survive remote outcomes.
Origin removal does not invalidate browser or CDN caches.

Upload/check/reconcile need object HEAD/GetObject and PutObject access; public-read
also needs PutObjectAcl. Deletion needs DeleteObject; immutable version removal needs
GetObjectVersion/DeleteObjectVersion. Versioning checks need GetBucketVersioning.
Object Lock/MFA restrictions may prevent removal. Missing list permission may make a
missing HEAD return 403, which is deliberately inconclusive rather than absence.

`testDestination` requires a setup caller supplied DurableCheckpoint. The caller must
durably acknowledge synthetic upload intent, confirmed receipt and every cleanup
step, preserving the exact target/progress for retry or restart. It creates only private synthetic text, conditionally uploads a unique
key, performs an unauthenticated direct GET and compares exact bytes, then attempts
guarded removal of its confirmed receipt. Its result includes upload/public/cleanup
outcomes and the exact receipt/progress if cleanup is blocked or uncertain. The setup
caller must retain those results for recovery. This API does not test live cloud in
ordinary startup/configuration validation; no actual user capture is involved.

Offline fixture tests verify actual SDK signatures, emitted conditional headers,
ACL/storage/content settings, bytes, encoded paths, lost replies, races, versioning
steps and returned effects. They prove no real AWS policy/custom-domain reachability
or desktop support. Live synthetic acceptance is a separate authorized gate.
