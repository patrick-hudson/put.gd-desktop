# S3 adapter

The official pinned AWS C++ SDK performs S3 signing and HTTP requests. AWS headers
remain under the S3 implementation. Shared acquisition, archive, operation, history
and CLI services use provider-neutral requests and receipts.

Each profile/revision supplies its bucket, region, endpoint, object prefix, storage
class, ACL mode, addressing mode and optional public URL base. The development
configuration is an explicit import, never an automatically activated destination.
`public-read` sends its selected ACL; `omit` sends no ACL header. The adapter never
changes ACL selection, bucket policy, ownership, retention, versioning or DNS.
`AccessControlListNotSupported`, authentication and permission errors are terminal
setup outcomes with retained artifacts. Explicit public URL testing is independent.

Requests verify HTTPS certificates. Plain HTTP is accepted only for a literal
loopback address, enabling a local S3-compatible endpoint and offline fixture.
Path addressing handles dotted buckets, including put.gd. Virtual addressing rejects
dotted buckets and literal IP endpoints; auto selects virtual addressing only for
an AWS endpoint and a bucket without dots. Public URL keys encode each segment once.
An encoded custom base path, including `%2F`, is preserved. A custom share domain is
never an AWS signing endpoint. Without a custom base the effective S3 object URL is
derived from endpoint/addressing/bucket/key.

Calls dispatch on up to 32 lanes (one on non-Linux platforms), each with its own
dispatch thread and FIFO queue, so concurrent uploads (`limits.concurrentUploads`)
run in parallel; at most 32 requests are queued in total. A lane is added only when
every existing lane is busy, and keeps its worker thread afterwards.
On Linux, each accepted driver call uses a new `putgd-s3-worker` process. It runs
`QCoreApplication` and keeps pipe handling separate from its SDK owner thread;
its link graph still includes QtGui through shared artifact code. The resident
does not load AWS libraries. Other platforms retain the in-process module route.
Each SDK generation uses one SDK executor thread and at most eight cached client
configurations. A client keeps up to four connections, which only a multipart upload
sending parts in parallel uses; every other call uses one.
The SDK client retains a copied explicit credential generation. Old clients drain
before runtime shutdown. SDK automatic retries are disabled. Its supported Curl HTTP customization also
forces fresh/nonreusable connections for DELETE to prevent libcurl from transparently replaying
a marker-creating DELETE after a reused connection loses its reply. Each DELETE
therefore pays a fresh connection/TLS handshake cost; PUT and HEAD retain connection
reuse. The hook is [the SDK Curl customization API](https://github.com/aws/aws-sdk-cpp/blob/1.11.907/src/aws-cpp-sdk-core/include/aws/core/http/curl/CurlHttpClient.h).
Non-curl SDK builds retain their default HTTP factory and expose deletion as
unsupported until their transport replay semantics have been implemented/verified;
no non-Linux deletion acceptance is claimed. Uploads allow three
total transient attempts with the same immutable key, body and condition, reconciling
publication before another attempt. Explicit connect, whole-request and low-speed
limits come from the profile. Services suppress clipboard results after cancellation;
queued work and later request phases observe a transient cancellation flag. An
already-sent request drains and may have taken effect. No GUI thread streams artifacts
or waits on HTTP. Shutdown waits for resources; configured timeouts bound network work.

## Upload progress

The official AWS SDK's body callback reports the current retained file-stream position and its exact size. The adapter reports preparing, uploading and finalizing separately from the confirmed upload result. The position handles rewinds for redirects and new upload attempts without adding retransmitted bytes to the percentage. These are body bytes read by the transport, not server acknowledgements.

On Linux, the private worker retains one latest observation and normally allows one unacknowledged progress frame. A 250 ms timer forwards it; the final flush may add one final frame before the terminal result. Progress acknowledgements use the strict control-frame sequence and remain separate from durable deletion checkpoints and credential requests. The parent validates the phase and counters against the artifact total, and ignores observer exceptions. Progress neither writes the operation journal for each byte nor wakes an Activity window.

## Large files: multipart upload

Files up to 64 MiB upload with one conditional `PutObject`. Larger files use an
explicit S3 multipart upload (`CreateMultipartUpload`, `UploadPart`,
`CompleteMultipartUpload`), driven by the adapter rather than the SDK's
`TransferManager`. The explicit calls keep the precondition on the request that
publishes: `CompleteMultipartUpload` carries `If-None-Match: *` for a new object, or
the checked ETag in `If-Match` for an explicit overwrite, plus the expected object
size (`x-amz-mp-object-size`). `TransferManager` would buffer parts in heap memory,
retry and complete on its own executor with no conditional completion, and hide the
per-part uncertainty this adapter has to record.

Parts are 16 MiB, or larger in whole MiB when 10,000 parts would not hold the file
(S3 allows 5 MiB to 5 GiB per part, at most 10,000 parts and 5 TiB per object; the
provider reports that 5 TiB maximum, and import rejects larger files before copying).
Each part streams from the retained artifact through a 64 KiB read window, so a
50 GiB file uses the same memory as a 70 MiB one. Every part carries its
`Content-MD5`, so S3 rejects altered bytes (`BadDigest`), and the SigV4 payload hash
covers it again. `CreateMultipartUpload` sets the content type, storage class, ACL
mode and the `putgd-publication`/`putgd-sha256` metadata, so the completed object is
identified, reconciled and deleted exactly like a single-request upload, with the
same direct URL. When every part ETag is a plain MD5 (no SSE-KMS), the completed
object's ETag must equal the MD5 of the part MD5s with the part count; otherwise the
item stays unknown.

Parallel parts: a multipart upload sends its parts in order on one lane, inside the
upload slot its file holds (`limits.concurrentUploads`). When other slots sit idle and
no file waits for one, the resident lends them to the upload, which then sends that
many more parts at once, up to four parts in all. The worker learns the lent count
within about 100 ms; a lane past it finishes its part in flight and starts no other.
A file that needs a slot takes a lent one back at once, so a small action queued
behind a large upload starts as soon as it would without the loan; for a moment the
borrowed lane may still be finishing one part. Order does not matter for
correctness: the journal names only the upload, a part is retried under its own
number, completion lists the parts in number order, and the first error stops every
lane before the usual abort: parts still in flight on the other lanes are cut rather
than finished (#203).

Retries and uncertainty: each part gets up to three attempts. A part whose reply is
lost is simply sent again under the same part number, which replaces it; parts never
publish, so they never make an item unknown. Only an uncertain
`CompleteMultipartUpload` does: the adapter then checks the key with HEAD, completes
again if the object is still missing, and otherwise records the usual unknown status.
Cancellation and every failure that ends the attempt call `AbortMultipartUpload`,
so no parts keep using storage. When the abort itself fails, the error says so
(`incompleteUpload`). Cancel doesn't wait for the parts in flight (up to four with
borrowed lanes): each `UploadPart` carries an SDK continue handler that stops it
while its body is sent, and libcurl's progress callback stops one waiting for its
reply within about a second (#203). A cut part never published anything, so the
item fails rather than becoming unknown, and Retry sends the part again or keeps
the copy S3 lists. A single `PutObject` is never cut: once its body is sent it may
have published.

Interruption and resume: the upload ID, key, part size and artifact identity are
journaled durably on the history item before the first part is sent. A crash, a
killed worker or a supervision timeout cannot abort, so it leaves that journal.
An explicit retry first reconciles the key, then lists the uploaded parts
(`ListParts`), keeps those whose size and MD5 ETag match the retained file, and
sends only the rest. A journal for a different key or artifact is aborted, never
resumed. Without `s3:ListMultipartUploadParts`, the retry sends every part again
under the same upload. A bucket lifecycle rule that aborts incomplete multipart
uploads after a few days is still recommended as a backstop; put.gd never changes
bucket configuration itself.

Retiring a retained upload: when artifact cleanup removes a failed item's artifact,
after `retention.failedArtifactDays`, no Retry can resume its upload any more, so
cleanup first calls `AbortMultipartUpload` for the journaled upload ID. Cleanup runs
on **Clean artifacts** (`cache.clear`) and on its own a minute after the resident
starts and then hourly (#202). An automatic pass removes at most 50 expired
operations, following up a minute later when more remain, and logs each removal.
Cleanup skips active operations. Retry is refused while a manual cleanup runs; a
Retry (or a manual cleanup) that arrives during an automatic pass stops it at the
next operation and runs as soon as it ends, so cleanup never aborts an upload a
Retry is about to resume. The abort is best
effort and never keeps the artifact: when S3 refuses it (for example without
`s3:AbortMultipartUpload`, or with the credentials locked), the item's error gains
`incompleteUpload` and `abortError`, the journal stays, the cleanup result lists it
under `incompleteUploads`, History says so, and each later cleanup tries again until
the abort succeeds or S3 no longer has the upload. The user hears of each such upload
once (#226): the pass that first keeps it marks the item `incompleteUploadReported`
(saved with the item, so neither the hourly pass nor a restart repeats it) and words
a notice with the count, the bucket, the most the parts can hold, S3's reason and the
fix: allow `s3:AbortMultipartUpload`, or add a lifecycle rule that aborts incomplete
multipart uploads after a few days. An automatic pass posts it as **put.gd —
incomplete uploads left**; **Clean artifacts** shows it in History's status line.
Both return it as `incompleteUploadNotice`, and `diagnostics.artifactCleanup` keeps
the latest one. Clearing history only hides
records; the artifact and its journal stay retryable until cleanup retires them.

Request IDs: failed multipart requests carry S3's `requestId` and `extendedRequestId`
in the item error. With debug logging on, each successful part request is logged with
its IDs too, and the completion's IDs are logged at info level (see
[diagnostics.md](diagnostics.md)).

Permissions: `CreateMultipartUpload`, `UploadPart` and `CompleteMultipartUpload`
are authorized by `s3:PutObject` (and `s3:PutObjectAcl` for public read). Aborting
needs `s3:AbortMultipartUpload`; resuming needs `s3:ListMultipartUploadParts`.
Test connection creates, lists and aborts a synthetic multipart upload, sending no
part, and explains which of these permissions S3 denied. Error guidance names the
same permissions for denials at each multipart stage.

S3-compatible endpoints must implement multipart uploads with 5 MiB minimum parts
and conditional writes (see [S3-compatible services](#s3-compatible-services)). The
#57 pull request records a run against a local moto server
(`tests/performance/s3_upload_probe.cpp`); MinIO's community server is archived
and no longer distributed.

## S3-compatible services

put.gd needs conditional writes: `If-None-Match: *` (and `If-Match` for an explicit
overwrite) on `PutObject` and `CompleteMultipartUpload`, so an upload never
replaces another file. An endpoint that answers `501 NotImplemented` gets a
definite `s3_unsupported_request` failure, not an unknown outcome, and Test
connection says the service lacks conditional writes. Live acceptance (#145):
AWS S3 in rounds 6–8, Cloudflare R2 and Backblaze B2 on 2026-10-20
([evidence](evidence/2026-10-20-round11-s3-compat/README.md)).

- **Amazon S3:** everything above.
- **Cloudflare R2:** supported. Use the endpoint
  `https://<account-id>.r2.cloudflarestorage.com`, region `auto`, ACL **omit**,
  and the bucket's r2.dev domain or a custom domain as the public URL base (the
  S3 endpoint itself is not public). Conditional writes, multipart, ListParts
  resume, abort and History deletion all pass. R2 returns a version ID on every
  write but has no versioning: a request that names a version gets 501, and the
  bucket reports no versioning status. When that happens, put.gd checks and
  deletes the object as unversioned and records `versionless` in the deletion
  journal (#267). R2 ignores `If-Match` on `DeleteObject`, so on R2 the removal
  is guarded only by put.gd's HEAD check of the publication identity, SHA-256,
  size and ETag just before it, not by the DELETE itself. R2 also ignores
  `x-amz-mp-object-size`.
- **Backblaze B2:** not supported through the S3 API; use the
  [Backblaze B2 destination](b2.md), which uses B2's native API. Its S3 API answers 501 to `If-None-Match` and
  `If-Match` on `PutObject`, `CompleteMultipartUpload` and `DeleteObject`, so
  every upload fails at the publishing request and nothing is published. Parts of
  a refused multipart upload are aborted. put.gd does not upload without the
  condition. The S3 API also refuses B2's master application key; use an
  application key. The S3 service picker in Settings no longer offers Backblaze
  B2. A saved profile with a `backblazeb2.com` endpoint still loads, shows as
  "Other S3-compatible", and its endpoint hint says why uploads fail and points to
  the Backblaze B2 storage service ([pictures](evidence/2026-10-20-s3-drop-b2/README.md)).

## Linux SDK worker protocol

The helper is a fixed sibling executable after installation, or the exact target
in the current build directory. It receives no keys, payload bytes or endpoint
configuration through arguments or added environment variables. A private pipe
handshake binds its complete compiled build manifest, S3 module contract, transport
capability, role, random nonce and generation before activation. Frames use the
existing bounded private protocol; typed S3 payloads reject unsupported fields,
states, sequence numbers and domain values.

The parent validates each typed request before activation. Invalid input returns
a typed failure without starting a network effect; removal retains its supplied
progress. Child-side validation remains a second check. Transport uncertainty is
reserved for failures where the worker may have started an effect.

Reconciliation validates the identity fields it actually uses, without requiring
upload-only file metadata. Stat and deletion accept historical receipt URLs and
preserve the original deletion target; they identify the object through its saved
destination and object identity. New successful response receipts still require
the canonical public URL and complete verified identity.

Readiness and credential queries return to the live parent cache for the original
destination. They also occur after destructive checkpoints, so forgetting a
credential is not hidden by a startup snapshot. Artifact metadata names the
retained immutable file; the unchanged SDK driver verifies and streams that file.

A child checkpoint waits for the original parent's durable save callback. Its
acknowledgement allows the associated network effect only after persistence
succeeds. Late acknowledgements use shared mailboxes and cannot touch a departed
driver stack. Pipe closure wakes blocked child exchanges before SDK teardown.
Throwing checkpoint callbacks fail closed, including callbacks that acknowledge
and then throw before returning.

The SDK callback retains its typed result inside the child. After its method
returns, clients, driver and runtime are destroyed on their original SDK worker.
The main thread then joins that worker before sending the terminal result. The
parent acknowledges receiving the complete frame; the child exits normally. Only
a valid result followed by normal exit permits the parent's API callback. A
queued successor starts another child, even when the logical proxy is reused.

Startup and activation each have a 10-second limit. An active child sends a
heartbeat every second; 15 seconds of pipe silence while the parent can read
fails the request. Time spent inside a synchronous host checkpoint callback does
not count as child silence. While the child awaits a durable acknowledgement,
heartbeats pause and the parent's checkpoint bound replaces its silence check.
This prevents a long local save from building a heartbeat backlog. Silence timing
resumes when the parent sends the acknowledgement. Credential
and readiness exchanges have a minute to reply. A durable checkpoint has five
minutes to acknowledge, and the parent allows five seconds
for exit after a terminal frame. A heartbeat proves transport responsiveness,
not successful SDK progress, and does not extend the finite work budget.

A synchronous host callback runs on the parent's dispatch worker. Its checkpoint
and total elapsed limits are checked when it returns; these watchdogs cannot
interrupt a blocking filesystem call. Asynchronous acknowledgements remain
bounded while the parent reads the pipe.

That budget allows 1 HTTP call for name/stat/reconcile, 6 for a single-request upload
(plus three per part and 16 more for a multipart upload), 8 for removal
and 20 for destination testing. Each call gets the larger of the configured whole
request timeout or connect timeout plus low-speed interval, with one second of
margin. It adds five minutes per possible checkpoint (4 multipart upload, 8 removal,
12 destination testing), a minute of fixed margin, and a file hashing allowance: four passes at
16 KiB/s, with a minimum minute. This deliberately conservative I/O allowance is
a policy assumption, not a promise about every filesystem. Arithmetic is bounded
over the supported file-size and timeout domains. The allowance includes retained
artifact verification and up to three signed PUT attempts. Normal work does not inherit
the graphical image worker's ten-second limit.

Actual cancellation starts a separate cleanup grace: the per-call budget plus
five seconds, clamped to 30–120 seconds. Ordinary requests retain their normal
budget. A worker that still fails to drain is terminated and returns uncertainty.
Crash, invalid protocol, timeout, missing result or abnormal exit never authorize
automatic replay of a possibly sent PUT or DELETE. Deletion returns empty adapter
progress on transport failure so History retains its latest durable checkpoint.
Forced exit is failure evidence, not successful idle-memory cleanup.

The current worker is an optimization candidate until the documented native,
live-S3, fresh-repeat and cross-desktop acceptance gates pass. See
[the memory test protocol](testing-live-s3-memory.md).

Signed HEAD checks a proposed key; only the final conditional PUT guards the race. New objects use `If-None-Match:*`; explicitly
configured overwrite uses the checked opaque ETag in `If-Match`. A changed/deleted
precondition is never refreshed automatically. Shared naming checks all batch items,
handles original basenames/generated names, caps searches at 32 and handles
rename/skip/overwrite conflicts. It persists candidate, hash, item publication identity
and condition before PUT. The adapter verifies the retained private artifact and
streams it. Object metadata contains publication identity and SHA256; ETag is never
interpreted as SHA256. Lost successful replies and subsequent 412 recover only when
HEAD matches publication identity, hash and byte count. Inconclusive/foreign outcomes
after an ambiguous attempt retain unknown status at the same key. Stable keys do not
promise exactly one version in a versioned bucket.

Receipts contain the exact original non-secret destination, credential reference,
key, version ID, publication identity, SHA256, byte size, ETag and stored direct URL.
Delete never derives a target from the share URL or edited profile. Signed identity
checks precede mutations. Unversioned and mutable null-version removal use the saved
ETag; null-version deletion addresses `versionId=null`. A current immutable version
in an enabled bucket is first hidden by an ETag-guarded delete marker, then only its
recorded bytes are removed. A noncurrent recorded version is removed directly while
preserving the current replacement. Unrecorded versions are never listed or purged.
An original unversioned receipt with no recorded version ID cannot be retargeted
to a newly visible null version after bucket versioning changes; it returns
unsupported_safe_removal without DELETE. Mutable null deletion can reveal an older version; it removes only the recorded
null version and does not claim the public URL or all versions are erased.

Before creating a marker in a suspended bucket the adapter explicitly reads the
null version. Any unselected null object/marker or denied/inconclusive read returns
`unsupported_safe_removal` with no DELETE. Confirmed absence allows marker creation;
bucket versioning is rechecked before it. External bucket versioning changes remain
outside S3's object guard. The ETag precondition cannot distinguish an external
identical-content replacement; this is a documented residual S3 race, not full
version compare-and-swap.

Deletion checkpoints persist intent and result for each destructive step and await
acknowledgement before sending it. Partial removal retains the marker and returns
`hidden_version_retained`; retry targets exactly the recorded immutable version.
A lost removal reply reconciles the exact target. A lost marker reply stays
`delete_unknown`: S3 markers have no publication metadata, so current absence alone
cannot identify this operation's marker. Retry/restart never blindly creates another
marker or adopts a replacement. Permission, retention, MFA and precondition failures
are reported; no bypass is attempted. Local copies/history survive remote outcomes.
Origin removal does not invalidate browser or CDN caches.

Upload/check/reconcile need object HEAD/GetObject and PutObject access; public-read
also needs PutObjectAcl. Deletion needs DeleteObject; immutable version removal needs
GetObjectVersion/DeleteObjectVersion. Versioning checks need GetBucketVersioning.
Object Lock/MFA restrictions may prevent removal. Missing list permission may make a
missing HEAD return 403, which is deliberately inconclusive rather than absence.

`testDestination` requires a setup caller supplied DurableCheckpoint. The caller must
durably acknowledge synthetic upload intent, confirmed receipt and every cleanup
step, preserving the exact target/progress for retry or restart. It creates only private synthetic text, conditionally uploads a unique
key, performs an unauthenticated direct GET and compares exact bytes, then attempts
guarded removal of its confirmed receipt. Its result includes upload/public/cleanup
outcomes and the exact receipt/progress if cleanup is blocked or uncertain. The setup
caller must retain those results for recovery. This API does not test live cloud in
ordinary startup/configuration validation; no actual user capture is involved.

Offline fixture tests verify actual SDK signatures, emitted conditional headers,
ACL/storage/content settings, bytes, encoded paths, lost replies, races, versioning
steps and returned effects. They prove no real AWS policy/custom-domain reachability
or desktop support. Live synthetic acceptance is a separate authorized gate.

## Safe transport failure diagnostics

Production SDK failures retain numeric `sdkErrorType`, `curlCode`, the SDK's
`sdkRetryable` flag, a fixed `requestStage` and `elapsedMs` for the failing SDK
call. Existing HTTP status and allowlisted service codes remain unchanged.
`curlCode: -1` means no recognized numeric Curl prefix was available, including
SDKs with another HTTP backend; it is not a Curl error number. Raw SDK messages,
headers, credentials, endpoint strings and payloads are never exported. The
Curl parser accepts only the SDK's anchored `curlCode: N,` prefix with at most
three decimal digits. Stages and numeric domains are validated on the worker
wire protocol. Timing excludes subsequent durable journal acknowledgements.

These fields describe failures returned to the caller. They are not a trace of
all successful HTTP exchanges or failures recovered internally. The SDK's
retryability flag does not enable retries. Transport behavior, cancellation,
journal acknowledgement and normal-worker-exit requirements are unchanged.
External test logs must distinguish independently observed process identities
from the source contract that requires a normal child exit before a typed result.
They must label unavailable exit codes rather than infer them from `/proc` absence.

## Connection-test feedback

Test connection shows progress and completion on the Destinations page. Success
requires the existing synthetic upload, exact public GET and guarded cleanup gates;
valid credentials alone do not establish public-link or cleanup success.

SDK errors use application-owned guidance for invalid access-key IDs, mismatched
signatures, temporary tokens, clock skew, missing buckets, region/endpoint mismatch,
ACL incompatibility, stage-specific IAM/bucket-policy denials, DNS/connection/TLS
failures, timeouts and service failures. Raw SDK messages and arbitrary service
strings remain excluded. A 403 on object HEAD can mean denied credentials or
permissions, or a missing object without ListBucket; the UI does not claim to
identify which. Version reads/deletes also require the corresponding version
permissions, including a deletion targeting the null version. Simultaneous public
GET and cleanup failures report both problems; retained cleanup targets still
require reconciliation before retrying.
